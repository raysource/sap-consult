A1 概念与架构（对应 concept / WBS 2.3）

概念WBS 2.3

1. RAP 中，从数据库表到 Fiori 的标准链路顺序是？

表 → Behavior → CDS → Service Binding → OData V4
表 → Interface CDS → Projection CDS → Behavior → Service Definition → Service Binding → OData V4 → Fiori Elements
表 → SEGW → OData V2 → Fiori Elements
CDS → 表 → ABAP 报表 → SM30
WBS 2.3 给出的主线：Table → Interface CDS (ZI) → Projection CDS (ZC) → Behavior → Service Definition → Service Binding → OData V4 → Fiori Elements。SEGW/OData V2 是旧路线。

2. Sheet「RAP Layer」中，下列“层 → 对象类型”对应正确的是？

BO 层 → Service Binding
消费层 → Behavior Definition
服务层 → Root View Entity
BO 层 → Behavior Definition；消费层 → Projection View；服务层 → Service Definition / Binding
Basic/Interface 层放 Root View Entity，BO 层放 Behavior Definition，Consumption 层放 Projection View，Service 层放 Service Definition / Binding，UI 层是 Fiori Elements。
概念WBS 1.4

3. VDM 命名中 I / C / P 分别代表？

Interface / Check / Private
Input / Consumption / Public
Interface（接口）/ Consumption（消费投影）/ Private（私有）
Internal / Central / Projection
I_ 接口视图（可带行为）、C_ 消费视图（供 UI/OData）、P_ 私有视图。WBS 1.4 要求 ZI_→ZC_→ZP_ 三层都能说明。
概念必考

4. Composition 与 Association 的本质区别是？

Composition = 整体-部分（子随父增删，级联）；Association = 独立对象间的引用（可 to-one/to-many）
两者相同，只是写法不同
Association 有生命周期，Composition 没有
Composition 只能用于报表，Association 用于事务
Composition 是包含关系（父删则子级联删、不能脱离父创建），Association 只是导航引用。订单头→明细用 Composition，订单头→供应商用 Association（WBS 1.2）。

A3 Behavior 定义与实现（对应手顺③ / WBS 3.2〜3.7）

BDEFWBS 3.2

8. BDEF 写 managed implementation 意味着？

所有 CRUD 由开发者手写 SQL
标准 CRUD、保存、锁等由 RAP 框架自动处理
只能读不能写
必须使用 BAPI
Managed = 框架替你完成 create/update/delete 与 DB 持久化（WBS 3.2 备注「managed=フレームワークがDB保存を担う」）。
BDEF必考

9. field ( readonly : update ) PoNum 的含义是？

永远可写
永远只读
创建时可提供（或由编号填充），更新时客户端不可改
只在删除时可写
readonly:update = 创建阶段允许赋值，更新阶段只读。主键（如订单号）通常这样设，配合 early numbering。
DraftWBS 3.5

10. 启用 draft 后，“保存”与“正式生效”如何区分？

保存直接写正式表，无需其他步骤
保存 = 写日志
只有管理员能 Activate
普通保存只存草稿表，点击 Activate（激活）后才写入正式表
Draft 的 Save 只落草稿表；Activate 才写正式表。BDEF 中启用后框架自动生成草稿表并提供 Edit/Activate/Discard/Resume。
DeterminationWBS 3.3

11. Determination（派生/默认值）与 Validation（校验）的触发时机区别是？

Determination 在 modify 时（如 create）触发；Validation 在 save 时触发
Validation 在 create 触发；Determination 在 save 触发
两者都在 save 后触发
两者没有区别
Determination 用 on modify（自动补默认值：日期/创建人/状态）；Validation 用 on save（提交前检查：金额>0、供应商存在等）。
ValidationWBS 3.3

12. 校验失败时，handler 如何通知调用方？

直接 RAISE EXCEPTION 即可
写 MESSAGE ... TYPE 'E'
同时往 failed-xxx 与 reported-xxx（含 %msg）里追加条目
更新数据库回滚标志
RAP 用 failed（哪条数据失败）+ reported（对应消息，%msg 用 new_message_with_text 等构造）两个隐式参数传达错误。
ActionWBS 3.6

13. 声明 action ConfirmOrder result [1] self 的效果是？

动作不能返回值
动作执行后把更新后的自身实体作为 result 返回，UI 可立即刷新该行
必须返回一个新实体类型
自动弹出报表
result [1] self = 把当前实体（更新后）返回给调用方。这正是 WBS 3.6 备注「Action後のRefreshはResponse Entityで制御」。
NumberingWBS 3.7

14. Managed BO + draft 场景，主键编号一般用哪种？

只能 late numbering
编号只能在 SAVE 后由数据库自增
必须手工输入，无法自动
UUID（managed numbering）或早编号 early numbering（CREATE 时即获得主键）
Draft 行也需要主键，因此主键必须在 CREATE 时就确定：UUID 由框架生成，或 CHAR 主键用 early numbering + 番号范围。late numbering 是 unmanaged 的 SAVE 序列概念。
NumberingWBS 3.7

15. early numbering 方法（FOR NUMBERING）把新主键告诉框架的途径是？

把带 %cid 与主键的行追加到 mapped-实体 参数
直接 UPDATE 数据库
修改 entities 参数本身
调用 BAPI_PO_CREATE
编号方法通过 mapped 响应参数返回 %cid ↔ 新主键 的映射；框架据此继续后续操作。禁止在 behavior 方法里直接 UPDATE 表。
Draft必考

16. 关于 early numbering 与番号范围的跳号（gap）现象：

不会有跳号，号码保证连续
号码在创建草稿时就消耗，放弃草稿会造成跳号——这是正常行为
跳号说明程序有 bug
跳号会导致激活失败
Early numbering 在 CREATE 时取号，草稿被丢弃则号被浪费 → 跳号。生产上若必须无跳号（如发票号），需用 late numbering（unmanaged）或特殊设计。

保存业务数据

Service必考

18. Service Definition 与 Service Binding 的区别是？

没有区别
Binding 定义实体，Definition 定义协议
Definition 只用于 OData V2
Definition 声明暴露哪些实体；Binding 把服务绑定到具体协议（OData V4 UI/API）并生成 URL
SD 选实体（expose），SB 定协议（OData V4 UI/API）并产出可调用 URL。WBS 3.4：Binding 预览能看到 Fiori 列表即成功。

26. EML（Entity Manipulation Language）能做什么？

只能在 Fiori 里用
直接改 SAP 标准表
代替 SE11 建表
在 ABAP 程序中用 MODIFY/READ ENTITIES 对 BO 做增删改查（含 action/draft）
EML 是 ABAP 代码操作 BO 的官方接口（CREATE / READ / UPDATE / DELETE / EXECUTE action / draft 控制），本站代码页的 ZRAP_EML_DEMO 即示例。

28. 关于行为实现类（BIL）中直接写 SQL UPDATE 表：

推荐，性能好
禁止——应通过 EML（MODIFY ENTITIES / IN LOCAL MODE）操作，由框架统一处理锁与 draft
只在 validation 里可以
必须用 SE38 程序代替
