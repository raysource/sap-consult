概念与设计 — VC 是「构成引擎」，不是生产形态

读完这一页应能回答的 4 个问题 ① 一台泵的「容量 80 / SUS316 / 涂装 EPOXY / 压力计＋流量计」是怎么变成 BOM 的 6 个零件和 3 道工序的？（→ 依存関係） ② 为什么不能把 VC 当成第 4 种生产形态？（→ VC × 生産形態 = 组合） ③ 加价是从哪里冒出来的？（→ 変種価格 VA00 と特徴の追加データ） ④ 换到 S/4HANA（AVC）之后，哪一部分的工作方式变了？（→ PMEVC・特徴グループ・MMCOM-VKOND）

3. 依存関係 4 種と適用先

依存関係は「式（構文）＋ 適用先（どこに貼るか）」の 2 点セットで覚えます。同じ式でも貼る場所で意味が変わります。

種類何を決めるか適用先（貼る場所）本站的例子
前提条件
Precondition		値が「使えるか／選べるか」を判定。満たさなければエラー、または値が不採用になる特徴 または 特徴値（CT04 から CU01 で作成して貼る）塗装 EPOXY は材質 SUS316 を要求（FC200 では選べない）
選択条件
Selection condition		BOM 明細・作業手順の工程などを「今回の構成に採用するか」を判定BOM 明細（CS02 の構成品目 → 選択条件）／工程（CA02）圧力計は付属品 PG または PG_FG のときだけ採用
手続き
Procedure		値を計算・上書きする（他特徴を自動セット、数量や標準値を書き換える）特徴値／BOM 明細／工程（標準値の書き換え）容量 120 のときモータ数量を 2 に、組立標準時間を 1.4 倍に
アクション
Action		設定の結果を使って他のオブジェクトを操作する（出力・伝票項目への転記・外部連携など）特徴値（稀に集中依存関係／引用経由）発展課題（本站不做実装，只做説明）
【前提条件の例】材質 SUS316 を要求する塗装値に貼る
   $SELF.ZVC_MATERIAL = 'SUS316'

【選択条件の例】流量計の BOM 明細に貼る
   $ROOT.ZVC_ACCESSORY = 'FG' OR $ROOT.ZVC_ACCESSORY = 'PG_FG'
   ※ BOM は「上位を参照する」ため $ROOT（最上位の設定可能品目）を使うのが基本。
     varconf の解説では階層の親を指す $PARENT.<特徴> = <値> の形で説明されている
     （どちらを使うかは BOM の階層とリリースで変わる → CS03 の選択条件画面で確認）

【手続きの例】容量 120 を選んだら付属品を自動セットする手続き（特徴値側）
   $SELF.ZVC_ACCESSORY = 'PG'
   ※ 「他特徴への値セット」は手続きの代表的な用途。数量・標準値の書き換えは
     BOM 明細 / 工程の「手続き」欄に貼る（項目名は自システムの画面で確認）
設計判断 ②：「選べなくする（前提条件）」か「選んだら他の値を直す（手続き）」か ① 前提条件で禁止＝ 客先に矛盾を見せない（エラーで止める）。教育コストは低いが、選択肢が消えると「なぜ選べないのか」を説明しにくい。
② 手続きで矯正＝ 片方を選べば他方が自動で正しくなる（EPOXY を選んだら材質を SUS316 に自動セット）。UX は良いが、 「勝手に変わった」と現場が混乱しやすい。
実務の勘所：物理的に不可能な組合せ＝前提条件、業務上の推奨＝手続き。この切り分けを最初に合意せずに作り始めると、後で必ず作り直しになります。
つまずき：依存関係が発火しない 3 大原因 ① 適用先が違う（選択条件を特徴に貼った／前提条件を BOM に貼った）→ 実際の貼り付け先を CU03（照会）と CS03/CA03 で確認。 ② 特徴名（技術名称）の綴り／大文字小文字が違う → CU50 で値を選んでも無反応ならここ。CT04 の技術名称をコピーして貼る。 ③ 設定プロファイルに「依存関係のチェック」が無い／再構成していない → CU50 のメニューで再構成、または受注を VA02 で開いて再構成（設定値の変更統制の論点。→ 练习⑤）。

4. クラスと分類（クラス型 300）

VC の「クラス」は SAP の分類システム（Classification）の一部です。クラス型（Class Type）で用途が決まり、VC では 300（品目変種 / Variant class）を使います。 他の型（例：023 は品目バッチ、001 は品目一般）と混ぜると、品目の分類ビューでクラスが出てこないなどの症状になります。

要素役割確認のしかた（自システム）
クラス型 300品目変種用のクラス型。CL02 の初期画面で選ぶCL02 → クラス型の F4。クラス型の定義は SE11 の TCLA 系＋IMG（分類システム）で確認
クラス ZVC_PUMP_CL特徴の入れ物。複数特徴を割り当て、必要数（必須）を制御するCL03 → クラス ZVC_PUMP_CL：特徴タブに 4 特徴
品目への割当品目マスタの分類ビューでクラスを割り当てる（VC の必須条件）MM03 → 分類ビュー → クラス ZVC_PUMP_CL
特徴の「必須」フラグ未入力で設定を終われなくする（＝完全性チェック）CL02 の特徴行（必須列）／CT04 の基本データ、そして CU50 での挙動
なぜ「クラス」が要るのか（設計の意味） 特徴を品目に直接貼るのではなく、クラスを経由させることで「同じ質問票（クラス）を複数の品目で使い回せる」「クラスを差し替えるだけで質問構成を変えられる」という柔軟性が得られます。 実務では「ポンプ共通クラス ＋ 機種別クラス」のようにクラスを分け、必須特徴だけを共通クラスに置く設計が定番です。

5. スーパー BOM と受注 BOM — 設定プロファイルの処理形式は「設計判断」

ここが VC で最も設計判断が効く場所です。スーパー BOM（CS01）には全バリエーション分の構成品目を入れておき、 受注の設定値で選別する——その「選別結果をどこに置くか」を決めるのが設定プロファイルの処理形式です。

処理形式（通常の呼称）受注明細での振る舞い向いている場面トレードオフ
明細 / 生産指図（BOM 展開なし）受注には構成品目が出ない（親品目だけ）。BOM は MRP・指図側で展開構成は製造都合、営業は完成品だけ売る受注画面が軽い代わりに、営業が構成結果（部品）を確認できない
伝票明細（SET 処理）構成品目が個別の明細（子明細）として並び、価格・所要量も明細単位で転送客先が部品構成（例：モニタ・CPU・キーボード）を選ぶ商売価格と所要量が子明細に分散。品目カテゴリグループ 0004 が前提（varconf）
受注 BOM（Order BOM）受注ごとに BOM のコピーを作り、手で追加/削除/差し替えできる。結果指向型と知識指向型がある受注ごとに設計変更・追加工がある（まさに本场景のポンプ）「受注ごとの BOM」を持つため管理すべきオブジェクトが増える（変更統制が重要）

出典：varconf.com Make-to-Order with SAP Variant Configuration（処理形式の 3 分類と受注 BOM の 2 副型、BOM 展開レベル）。本站练习②〜④ は 受注 BOM を選びます（受注 BOM を見せる練習になるため）。

設計判断 ③：受注 BOM / SET / 展開なし のどれを選ぶか 判断の順序：① 客先に見せる必要があるか（YES なら SET か受注 BOM）→ ② 受注ごとに構成を手で直すか（YES なら受注 BOM）→ ③ 子明細に価格と所要量を持たせるか（YES なら SET、0004 が必要）。
やってはいけないのは、後から処理形式を変えること（受注 BOM を作ってから SET に変えると、既存受注の構造と価格転送が壊れる）。最初に決めて、受注を流す前に固めるのが鉄則です。

6. 設定値の流れ（受注 → 出荷 → 請求）

設定値（構成）は受注で確定し、MRP→指図へと「継承」されていきます。継承が切れると「受注では SUS316 なのに指図では FC200」という最悪の状態になります。

1
VA01 明細の構成画面で値を選択依存関係が発火 → 前提条件で矛盾を排除・手続きで数量や価格キーを確定
2
受注 BOM（構成品目）が確定スーパー BOM の明細から、選択条件を満たす行だけが残る（VA03 → 明細 → 構成品目）
3
所要量 → MRP → 計画手配戦略 25 なら所要量タイプ KEK・受注在庫（特別在庫 E）。計画手配は設定を引き継いで生成される
4
製造指図に構成が伝搬CO03 の「構成」で設定値・構成品目・工程を確認。選択条件は指図の BOM/工程にも効く
5
入庫 → 出荷（601）→ 請求受注在庫（E）から出庫確認し、請求には変種価格の加算が乗る
确认的 4 个证据（実機での勘所） ① VA03 の明細：構成（設定値）と構成品目（受注 BOM）。 ② MD04：受注明細の所要量（得意先所要量）と計画手配の在庫区分。 ③ CO03：指図の構成（設定値）と BOM/工程が設定どおりか。 ④ VA03 の条件画面：VA00 の加算行があるか（無ければ → 第 8 節）。

7. VC × 生産形態（VC は単独では存在しない）

組合せ戦略グループ / 所要量タイプ所要量クラス / 指図タイプ库存区分場面
VC × MTO（本站主场景）25 / KEK046 系E（受注在庫）得意先が仕様を選ぶ受注生産（産業機械・ポンプ・エレベータ）
VC × ATO（組立処理）82 / KMFA201 / PP04E または 自由在庫＋指図受注と同時に指図を立て、短納期で組む（BOM 必須・1:1）
VC × ETOETO 用の戦略（Cloud は E2）＋ WBS 割当—Q（プロジェクト在庫）案件ごとに設計し、仕様選択もある
VC × 見込生産戦略 10/20/40＋ PIR独立所要量系自由在庫バリエーションを予測で作る（設計は要検討）
覚えるべきは 2 本の線だけ（残りは表を見る）
  戦略 25 ──► 所要量タイプ KEK ──► 所要量クラス 046 系 ──► 受注在庫 E       ← VC × 受注生産
  戦略 82 ──► 所要量タイプ KMFA ──► 所要量クラス 201 ──► 指図タイプ PP04    ← VC × 受注組立（1:1・BOM 必須）
確認：OPPS（戦略グループ）／OPPJ（計画方針）／OVZG（所要量クラス・所要量タイプ）で自システムの値を照会
よくある勘違い 「VC だから受注生産」は誤りです。VC は構成エンジンで、戦略グループは別に決めます。25 と 82 の差は受注と指図の関係（1:1 で受注時に指図を作るか、MRP 経由で後から作るか）で、ここを取り違えると 「受注した瞬間に指図ができてしまう／できない」という症状になります。→ 练习⑤ で両方を体験します。

8. 変種価格の仕組み（加算はどこから来るか）

VC の加算は、「設定値 → 価格のキー（VKOND）→ 条件レコード」の 3 段で決まります。基本価格（PR00）は通常の価格で、オプション選択による加算は VA00（変種条件）が担当します。

段何をするかT-code確認のしかた
1. 価格用特徴の準備特徴の追加データに「テーブル／項目」を指定し、その特徴の値が条件キーとして使われるようにする（LO-VC は SDCOM-VKOND、AVC は MMCOM-VKOND という記載）CT04（追加データタブ）CT04 で該当特徴を開き、追加データのテーブル/項目を確認。SE11 で構造の実在を確認
2. 条件タイプと計算手続VA00 が「変種条件」として使われ、計算手続の中で参照される（加算型にするか小計型にするかは設計判断）V/06（条件タイプ）・V/08（計算手続）V/06 で VA00 の属性、V/08 で手続内の順序・ステップ番号を確認
3. 条件レコード特徴値ごとに金額を持つ（例：SUS316 = +120,000）。キーは上記の項目（VKOND）VK11（VK13 照会）VK13 で VA00 の条件レコードを一覧。受注の VA03 の条件画面で実際に決定されているかを見る
価格決定のイメージ（本站练习値）
  PR00   850,000 JPY × 10 台 = 8,500,000   ← 基本価格（条件レコード）
  VA00   材質 SUS316   +120,000 × 10 台    ← 変種条件（特徴値がキー）
  VA00   塗装 EPOXY     +35,000 × 10 台
  VA00   付属品 FG      +48,000 × 10 台
  ------------------------------------------------
  合計（税抜）          1,053,000 / 台  → 10 台 10,530,000 JPY
  ※ 金額・加算の有無はあくまで例。実システムでは VK13 の条件レコードが正
つまずき：加算が出ないときの順序 ① 受注の条件画面に VA00 の行が無い → 計算手続（V/08）か条件タイプの有効性。 ② 行はあるが金額 0 → 条件レコード（VK11）のキーが設定値と一致していない（＝VKOND に値が入っていない）。 ③「値は入っているのにキーが空」→ 特徴の追加データ（テーブル/項目）が未設定、または参照特徴（Reference characteristic）の設計ミス。 SAP KBA 1934081 も、標準ではVKOND を参照する特徴の値が変種条件行 VA00 を決めると説明しています。

9. LO-VC と AVC（S/4HANA での違い）

観点LO-VC（従来）AVC（S/4HANA の現行）
位置づけSAP ERP 以来的标准 VCS/4HANA の「現行」バリアント設定プラットフォーム（性能・統合・UI を強化）
モデリング環境CU41・CT04・CL02・CU01 などの個別画面中心PMEVC（統合モデリング環境）。従来画面も併存し、習得済みナレッジは活かせる
設定画面（UI）CU50 などのクラシック画面特徴グループ（Characteristic Groups）＋ Fiori アプリに置き換わるという記載（varconf）
価格のキー項目SDCOM-VKONDMMCOM-VKOND という記載（自システムで CT04 の追加データと SE11 を確認）
制約（Constraints）手続き中心のロジック制約ネット（CU21/CU22/CU23 系）を使った宣言的な整合性チェックが現実的になる（varconf の AVC 解説）
材料バリアント—S/4HANA のスイッチ VCHMOVMVAR で材料バリアントの扱いを切替（varconf）
本站的扱い概念は LO-VC の用語で説明し、AVC との差はその都度注記します。実装前に「どちらの環境で作るか」を先に決めるのが原則（移行時は Simplification List の確認が必須）
設計判断 ④：LO-VC で作るか AVC で作るか ① 既存資産とスキルが LO-VC なら、無理に移さない（移行そのものがプロジェクトになる）。② 新規で複雑な製品（多品種・制約が多い）なら AVC の特徴グループ＋制約が効く。 ③ Public Cloud は AVC が前提。この 3 点で判断し、判断結果を設計書の冒頭に明記してください（後続の全手顺に影響します）。

12. 10 の誤解（面接・現場で必ず出る）

#誤解正しい理解
1VC は生産形態のひとつVC は構成エンジン。生産形態は戦略グループ／库存区分で別に決める（25 / 82 / ETO）
2KMAT は在庫になる原則として KMAT は在庫管理されない。在庫は構成品目／製造された実体（受注在庫 E など）で持つ
3特徴を品目に直接貼る必ずクラス（型 300）経由。品目には分類ビューでクラスを割り当てる
4設定プロファイルは「設定画面の見た目」だけ処理形式（BOM の扱い）と必須チェックを決める設計の中枢。ここを間違えると受注 BOM が出ない
5依存関係は 1 種類しかない前提条件・選択条件・手続き・アクションの 4 種で、貼る場所（適用先）が違う
6BOM は受注時に自動で作り直されるスーパー BOM を事前に作り、選択条件で絞る方式。受注 BOM はそのコピー（＋手修正）
7加算価格は品目マスタに入れる加算は 条件タイプ VA00 ＋ 条件レコード。特徴の追加データがキー（VKOND）になる
8設定を変えても製造は自動で追従する変更には再構成・再展開が必要で、業務ルール（ロック・再計画）を決めなければ現場が壊れる（练习⑤）
9VC を入れれば品目マスタが減る減るのは「完成品の品目」だけ。特徴・クラス・依存関係・スーパー BOM という新しい設計資産が増える（維持コストを認める）
10AVC にすれば全部よくなるAVC は道具。良し悪しを決めるのは特徴の粒度と依存関係の設計。道具を変えても設計は自動で良くならない
